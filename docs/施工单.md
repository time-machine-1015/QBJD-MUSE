# QBJD MUSE 改造施工单（免费方案 · 已确认）

## 一、为什么旧版会出问题（实测结论）

| 现象 | 真实原因 | 证据 |
|---|---|---|
| 点赞/评论/故事越用越少 | 前端把整份 `likes.json` 读出来改完再整体覆盖写回，两人同时操作后写的抹掉先写的 | 仓库 43 条提交里每条点赞/评论各是一个提交，写入无并发保护 |
| 照片刷新不出来 | 上传 = 等 GitHub 重新构建部署（几十秒~几分钟），期间图片 404；Service Worker 又把失败的缩略图永久缓存 | `sw.js` 里缩略图"缓存优先 + 缓存名固定" |
| 点赞同步慢 | GitHub Pages 的 CDN 缓存 `max-age=600` | 实测线上响应头 |
| 密钥泄露 | GitHub 写权限 token 就放在公开仓库的 `data/settings.json` 里 | 可直接还原出 token |
| Supabase 当年"时断时续" | 该域名在国内直连被重置 | 不走代理实测 `ECONNRESET` |

## 二、新架构（全部实测可达、成本 0 元）

```
手机 App（Android）
  │  读：GitHub Pages          …… 实测 267ms，免 token、不限次数
  │  写：Deno Deploy 云函数     …… 唯一写者，token 只在服务端
  │  推：MQTT（broker.emqx.io）…… 实测可直连，通知秒到
  │  兜底：每 60 秒拉 state/version.json（几十字节）
```

- 前端外壳：GitHub Pages（现有 `QBJD-MUSE` 仓库），网页改动 8 台手机**无需重装**即可生效
- 数据：新仓库 `QBJD-MUSE-data`（只有照片、快照、评论、收件箱，无任何密钥）
- 写入：一次操作 = 一个提交，且带"别人抢先提交就整段重做"的并发保护
- 通知：五类事件（别人上传照片 / 别人赞你的照片 / 别人评论你的照片 / 别人赞你的评论 / 别人回复你的评论）
